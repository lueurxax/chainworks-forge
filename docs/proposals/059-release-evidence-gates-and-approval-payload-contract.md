## 1. Context and Motivation

Run `9318de0d-9c75-40ad-9d0a-74c3610b021d` reached manual release approval after code-owned implementation work completed. Remaining blockers were operator-owned release evidence:

- W4-02 release-gate evidence artifact had placeholder values.
- Named evidence owner was `TBD`.
- 12 unit test invocations and 10 UI test invocations were not fully recorded in the release evidence artifact.
- CloudKit owner/invitee manual smoke remained unchecked.
- Phase 5 checklist items for manual smoke, AccessibleColors audit acknowledgement, owner assignment, and go/no-go were unchecked.

This was operationally acceptable only because an operator manually inspected and updated the run narrative. A future UI or self-service workflow needs typed gate payloads that say exactly what is pending, what can be executed automatically, what requires a human, and whether approval would be a normal approval or an explicit override.

---

## 2. Problem Statement

### 2.1 Release evidence is prose-driven

Checklist files and proposal text describe evidence requirements, but the control-plane does not own a typed release gate model. Agents and operators can create placeholder artifacts that look structurally present while containing `TBD`, nulls, fake build metadata, or unchecked items.

### 2.2 Manual approval lacks structured evidence context

`state_11_manual_release` approval currently asks for a decision but does not require an approval payload containing:

- code gate status
- release evidence status
- pending manual evidence
- known non-blocking risks
- stale artifact warnings
- whether approval bypasses any evidence blocker

### 2.3 Automated and manual evidence are mixed

Some release evidence can be executed by the control-plane:

- xcodebuild unit tests
- xcodebuild UI tests when environment is available
- static artifact validation
- checklist completeness

Other evidence is genuinely manual:

- CloudKit owner/invitee signed-in smoke
- App Store Connect account operations
- human go/no-go decision

The workflow should distinguish these classes instead of handing all of them to a model or operator as prose.

P059 includes:

- typed release gate requirement schema
- typed approval payload generated by the control-plane
- placeholder/TBD evidence detection

- manual evidence item model
- explicit approval override semantics
- MCP/GraphQL readback for release gates and approval payloads

P059 does not include:

## 4. Release Gate Model

Add a typed release gate artifact:

```json
{
  "schema_version": "release-gate.v1",
  "run_id": "...",
  "gate_id": "w4_02_family_sharing_release_evidence",
  "status": "blocked_pending_evidence",
  "requirements": [
    {
      "id": "w4_unit_matrix",
      "kind": "automated_command_matrix",
      "owner": "control_plane",
      "status": "pending",
      "required": true
    },
    {
      "id": "cloudkit_owner_invitee_smoke",
      "kind": "manual_smoke",
      "owner": "operator",
      "status": "pending",
      "required": true
    }
  ]
}
```

Allowed requirement kinds:

- `automated_command`
- `automated_command_matrix`
- `static_artifact_validation`
- `manual_smoke`
- `manual_attestation`
- `named_owner_assignment`
- `go_no_go_decision`

Allowed statuses:

- `pending`
- `running`
- `pass`
- `fail`
- `blocked_environment`
- `blocked_missing_owner`
- `waived`

`waived` requires an approval override reason and must be visible in release receipts.

## 5. Evidence Artifact Validation

The control-plane validates release evidence artifacts before any manual approval request is generated.

Invalid evidence examples:

- field value equals `TBD`, `TODO`, `placeholder`, or empty string where concrete value is required
- `owner` is `TBD` or role-only when a named individual is required
- test invocation has missing command, destination, started_at, finished_at, or result
- manual smoke result has no actor, environment, timestamp, or redaction attestation
- fake build metadata remains, for example `CryptoSavingsTracker-1.0.0-build-123`
- `overall_result: pass` while required items are pending/fail

Validation writes:

```json
{
  "schema_version": "release-gate-validation.v1",
  "gate_id": "w4_02_family_sharing_release_evidence",
  "status": "blocked",
  "blocking_items": ["owner", "unit_invocations[0]", "manual_smoke.owner_accepts_share"],
  "placeholder_count": 24
}
```

## 6. Automated Evidence Runner

For command-matrix gates, the workflow defines a matrix in structured data, not prose.

Example:

```json
{
  "id": "w4_unit_matrix",
  "kind": "automated_command_matrix",
  "scheme": "CryptoSavingsTrackerTests",
  "destination_resolver": "ios_simulator_uuid",
  "commands": [
    {
      "id": "family_sharing_copy_contract",
      "only_testing": "CryptoSavingsTrackerTests/FamilySharingCopyContractTests"
    }
  ]
}
```

Runner behavior:

1. Resolve destination UUIDs before execution.
2. Run each command with timeout and captured output.
3. Record exact command, destination, started_at, finished_at, result, failure_output.
4. Continue or stop according to gate policy.
5. Mark environment failures separately from test failures.

P051 may later provide host-user Xcode execution. Until P051 lands, the runner may use existing local execution only when environment preflight passes. If preflight fails, the gate becomes `blocked_environment`, not `fail`.

## 7. Manual Evidence Model

Manual evidence entries must be typed:

```json
{
  "id": "cloudkit_owner_accepts_invitee",
  "kind": "manual_smoke",
  "status": "pending",
  "actor": null,
  "environment": "cloudkit_sandbox",
  "redaction_policy": "owner_A_invitee_B",
  "required_fields": ["actor", "performed_at", "result", "notes", "redaction_attestation"]
}
```

The control-plane must reject `pass` manual evidence if required fields are missing or redaction attestation is false.

## 8. Approval Payload Contract

Before entering a manual approval stage, the daemon writes:

```text
{chainworks_meta_root}/approvals/current-request.json
```

Shape:

```json
{
  "schema_version": "approval-request.v1",
  "run_id": "...",
  "stage_id": "state_11_manual_release",
  "approval_policy": "manual_release",
  "code_gate_status": "pass",
  "release_evidence_status": "blocked_pending_operator_evidence",
  "required_operator_actions": [
    "record_named_w4_02_owner",
    "complete_cloudkit_manual_smoke"
  ],
  "automated_evidence_status": "pass",
  "manual_evidence_status": "pending",
  "stale_artifact_warnings": [],
  "approval_modes": [
    "approve_after_evidence_ready",
    "approve_with_explicit_evidence_override",
    "reject"
  ]
}
```

If release evidence is blocked, a normal release approval is not allowed unless the approval policy explicitly permits override. Override approval must include:

- reason
- acknowledged blocking items
- operator identity if available
- journal row
- release receipt warning

## 9. Required Behavior

### 9.1 Entering manual release gate

When a run reaches `state_11_manual_release`, the daemon:

1. validates implementation/code gates through canonical artifact contracts
2. validates release evidence gates through P059
3. writes `approvals/current-request.json`
4. creates an approval row with structured gate summary
5. exposes the same payload through MCP `approvals.list` and GraphQL approval readback

### 9.2 Approval resolution

Approving a blocked release gate without override reason is rejected.

Approving with override reason is allowed only when the workflow approval policy permits `manual_release_override`. The override is recorded in command journal and final release receipts.

### 9.3 Evidence runner invocation

The operator or lead can trigger automated evidence collection through a future MCP/GraphQL command. If P045 recovery tools are already present, this can be modeled as a run action rather than a separate workflow transition.

Minimum tool shape for implementation:

```json
{
  "name": "release.evidence.run",
  "input_schema": {
    "type": "object",
    "required": ["run_id", "gate_id"],
    "properties": {
      "run_id": { "type": "string" },
      "gate_id": { "type": "string" }
    }
  }
}
```

P059 may implement this MCP-first and add GraphQL later, or implement both if local UI needs it.

## 11. Proof Gate

`./scripts/test-gate.sh proposal-059` must include:

1. Placeholder validation test: `TBD` owner and fake build metadata block release gate.
2. Command matrix model test: required invocation records need command, destination, timestamps, result, and output fields.
3. Manual smoke model test: cannot mark `pass` without actor, timestamp, result, notes, and redaction attestation.
4. Approval payload generation test for code-pass/evidence-pending state.
5. Approval resolve test: normal approve rejected while required release evidence is pending.
6. Override approve test: override requires reason and records acknowledged blocking items.
7. Environment-blocked evidence runner test: simulator/Xcode preflight failure marks requirement `blocked_environment`, not test `fail`.
8. MCP/GraphQL parity test if both surfaces are implemented.
9. Gate registry test for `proposal-059|p059`.

The proof gate must not require live Xcode or CloudKit. Live command execution can be covered by a separate integration smoke after P051 host execution is ready.

---

## 12. Acceptance Criteria

- Manual release approvals include a structured payload with code gate status, release evidence status, and required operator actions.
- Placeholder release evidence cannot masquerade as complete evidence.
- Automated evidence requirements can be executed and recorded by the control-plane when environment preflight passes.
- Manual evidence remains explicit and typed instead of buried in markdown checklist prose.
- Approval with pending required evidence either fails or records an explicit override according to workflow policy.
- UI/MCP consumers can show exactly why a run is waiting for approval without reading raw docs/checklists.
