# Junie ACP direct probe, 2026-05-02

## Scope

This evidence records a direct local probe of Junie CLI ACP behavior before changing
Chainworks adapter code.

Local environment:

- Repository: `/Users/user/Documents/Chainworks Forge`
- Junie binary: `/Users/user/.local/bin/junie`
- Junie version: `1468.30`
- Probe date: `2026-05-02`

## External documentation checked

- JetBrains Junie ACP documentation: <https://junie.jetbrains.com/docs/junie-cli-acp.html>
- JetBrains Junie CLI reference: <https://junie.jetbrains.com/docs/parameters.html>
- JetBrains AI Assistant ACP configuration: <https://www.jetbrains.com/help/ai-assistant/acp.html>

The JetBrains documentation says Junie ACP mode is enabled with:

```console
junie --acp true
```

The local `junie --help` output agrees: `--acp=<[true|false]>`.

## Direct probe results

### Version and flag shape

`junie --version` returned:

```text
Junie version: 1468.30
```

`junie --help` shows:

```text
Acp:
  --acp=<[true|false]>  Run in ACP mode (Agent Communication Protocol) for IDE integrations.
```

### Initialize

Sending a newline-delimited JSON-RPC `initialize` request to plain `junie` produced no
JSON-RPC response within the direct probe window.

Sending the same request to each of these ACP launches returned an immediate
JSON-RPC response:

```console
junie --acp true
junie --acp=true
junie --skip-update-check --project "/Users/user/Documents/Chainworks Forge" --acp true
```

The response includes the standard `id` and `result` fields, plus a JetBrains
type discriminator:

```json
{
  "type": "com.agentclientprotocol.rpc.JsonRpcResponse",
  "id": 0,
  "result": {
    "protocolVersion": 1,
    "agentCapabilities": {
      "loadSession": true,
      "promptCapabilities": {
        "audio": false,
        "image": true,
        "embeddedContext": true
      },
      "mcpCapabilities": {
        "http": true,
        "sse": true
      },
      "sessionCapabilities": {
        "fork": {},
        "list": {},
        "resume": {}
      },
      "auth": {}

    "agentInfo": {
      "name": "@jetbrains/junie",
```

The current Rust handshake reader keys on `id`, `error`, and `result`, so this
extra `type` field should not itself block parsing.

### Session creation

After successful `initialize`, `session/new` succeeded with the Chainworks-shaped
params:

```json
{
  "mcpServers": [],
  "cwd": "/Users/user/Documents/Chainworks Forge",
  "model": "default",
  "mode": "bypassPermissions"
}
```

`session/new` also succeeded with `mode: "autonomous"` and `mode: "interactive"`.
Therefore the immediate blocker is not the current Chainworks `mode` value.

### Minimal prompt

After `session/new`, a minimal `session/prompt` request:

```json
  "prompt": [

      "type": "text",
```

One streamed `agent_message_chunk` contained `OK`.

## Current Chainworks mismatch

The Rust control-plane Junie adapter currently launches only the Junie binary:

```rust
Ok(AcpLaunchSpec::new(&self.binary_path))
```

It does not pass `--acp true`.

By contrast, the Gemini ACP adapter already has an explicit ACP launch argument
and a test asserting that behavior.

## Conclusion

Junie CLI itself is usable through ACP on this machine. The direct probe reached
`initialize`, `session/new`, and a minimal `session/prompt`.

The likely root cause of Chainworks Junie ACP failure is our launch shape, not
Junie availability and not the basic Chainworks `session/new` payload. The next
implementation should make the Junie adapter launch ACP mode explicitly and add
tests that would have caught the missing launch arguments.

The old Swift app-side ACP transports are no longer an active execution path.
Live provider execution belongs to the Rust control plane; the Swift app reads
run state through GraphQL and artifacts on disk.

## Proposed implementation plan

1. Update `control-plane/crates/acp/src/adapters/junie.rs` to launch Junie in
   ACP mode with `--acp true`.
2. Add Rust adapter tests equivalent to the Gemini launch tests:
   - launch spec includes `--acp` and `true`;
   - fixture execution still succeeds when the wrapper ignores Junie-specific
     launch arguments.
3. Add a gated live smoke check for Junie ACP, disabled by default and enabled
   only through an explicit environment variable, that verifies
   `initialize -> session/new -> session/prompt` against the local Junie binary.
4. Remove the legacy Swift app-side ACP transports from current code and keep
   Rust control-plane adapters as the authoritative runtime path.
5. Rebuild/restart the daemon after the adapter fix, then rerun the existing
   `.chainworks/operator-smoke/junie-gemini-smoke-*` workflow as the end-to-end
   verification.
